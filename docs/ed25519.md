# `std.ed25519`: sign and verify, checked against real `openssl`

> **Status: built.** `docs/sha512.md` §5 named this as the slice SHA-512
> was a prerequisite for and deliberately did not start: field
> arithmetic `std.bignum` could not do, curve point operations, and a
> constant-time posture nothing here provides. All three are answered
> below — the first two built, the third answered **no**, honestly,
> not deferred a second time.

---

## 1. What this is for, and what it is not for

`lex-os-capsule` signs a capability contract with Ed25519
(`ed25519-dalek`, in Rust) so a consumer can verify *what it is
installing* before trusting it. Porting that runtime onto lex-sys
(`docs/crypto.md` §1's own opening move) eventually needs the same
primitive reachable from `.ls` code — a future `lex-os-guest` written
in lex-sys, not lex-sys's own Rust tooling.

**This module is not what `crates/lex-sys-vcs` uses to seal its
attestation chain.** That is Rust code sealing a Rust data structure;
`ed25519-dalek` is already the right tool there, the same way
`lex-os-audit` already uses it, and reaching for this module instead
would mean trusting hand-rolled, non-constant-time arithmetic for a
job an audited crate already does correctly and safely. This module
exists for the day a `.ls` program itself needs to sign or verify —
which today means only the port target above, not yet a real
consumer in this repository.

---

## 2. Representation: correctness over speed, throughout

Curve25519 field elements are usually packed into a handful of wide
limbs (radix 2^25.5 or 2^51) so a multiply's cross terms fit efficient
hardware multiplication with room for lazy carrying. That representation
is exactly the kind of carry-chain arithmetic `docs/sha512.md` §2 already
found one real, non-obvious bug in for a *simpler* operation (a 64-bit
rotate). Ed25519's own arithmetic — field inversion, point addition,
scalar multiplication — is `sha512.md`'s bar raised by orders of
magnitude: hundreds of field operations, each one a fresh chance to get
a carry-chain detail wrong in a way four vectors might not catch.

So this module makes one deliberate trade, everywhere: **a "big number"
is a little-endian `[byte]` slice — usually 32 bytes — and every
operation on one is bit-serial.** `bn_reduce_wide` reduces a wide value
mod a fixed modulus one bit at a time: shift the running remainder left,
bring in the next bit, subtract the modulus back out if the remainder
reached it. `bn_modpow` is ordinary left-to-right square-and-multiply,
walking every bit of the exponent whether or not it is set. Both are
asymptotically worse than a radix-limbed implementation and neither has
a carry chain to get subtly wrong — the whole toolkit is compare, add,
subtract, shift-by-one, and schoolbook multiply, four operations simple
enough that `bn_test`'s own hand-computed cases (`200 * 300 mod 1000`,
`3^4 mod 7`, `5 - 3 mod 7`) were enough to catch the one real bug it had
(§4).

Field arithmetic (`gf_add`/`gf_sub`/`gf_mul`/`gf_invert`/`gf_pow2523`) is
this toolkit fixed to the field modulus `p = 2^255 - 19`. Scalar
arithmetic (`k*a mod L`, `r + k*a mod L`) is the same toolkit fixed to
the group order `L` instead — one set of primitives, two moduli, rather
than a second implementation for the scalar side the way a
performance-first design would need.

A point is one 128-byte buffer — extended coordinates `(X, Y, Z, T)` as
four consecutive 32-byte fields, `X*Y = T*Z` — so a point is a single
region parameter to pass around rather than four kept in sync by hand,
and `p[0..32]`/`p[32..64]`/etc. read a coordinate the same way any other
subslice does. `point_add` is the one unified formula, used for both
addition and doubling (`point_scalarmult`'s own double-and-add), checked
independently in Python before any of this was written: repeated
doubling-and-adding of the base point by the group order `L` returns the
identity.

## 3. Constants, derived, not transcribed

`p`, the group order `L`, the curve parameter `d`, a square root of
`-1` mod `p`, and the base point `B`'s own compressed encoding are each
a 32-byte `static`. None were copied from a reference implementation or
from memory: `d = -121665/121666 mod p`, `B`'s coordinates from
`y = 4/5 mod p` and the curve equation, both computed directly (modular
inverse via Python's `pow(x, p-2, p)`) and checked before being written
down — `B` is confirmed on the curve, and `L * B` computed by repeated
doubling-and-adding reduces to the identity, the same check §2 already
described as this module's own point-addition proof.

The two literal-syntax findings `docs/sha512.md` §2 made — a full
64-bit word with its top bit set does not parse, and `(1 << 63) - 1`
traps rather than producing `int::MIN`'s low 63 bits — do not recur
here: every constant is stored byte by byte (`byte_of(0x..)` on a
`[byte]`, never a 64-bit `int` literal), so no individual value ever
approaches either ceiling.

## 4. The one real bug, and how it was found

`bn_modpow` and `sign`/`verify` reuse one scratch buffer across many
calls — once per bit of an exponent, once per step of a signature.
`bn_reduce_wide`'s first version assumed its output buffer arrived
zeroed and left it to the caller, the same contract `alloc_slice`'s own
zero fill gives a *fresh* buffer. A reused buffer is not fresh: `3^1 mod
7`, computed by hand-inlining `bn_modpow`'s own loop with the actual
scratch buffers it uses, returned `1` instead of `3` — correct in
isolation (`bn_mulmod` on freshly-allocated buffers, tested first, gave
the right answer every time), wrong the moment the same `scratch`
buffer was asked to hold a second, unrelated reduction without being
cleared first.

Fixed by zeroing `o` at the top of `bn_reduce_wide` itself, so the
function's own contract no longer depends on which of its callers
remembered to clear a buffer before reuse. `3^0` through `3^4 mod 7`
(`1, 3, 2, 6, 4`) and the original three-case hand check both pass
after the fix, and every downstream layer built on `bn_reduce_wide` —
field arithmetic, point arithmetic, sign, verify — was re-checked
against real `openssl` output afterward rather than assumed fixed by
association.

## 5. Checked against real `openssl`, in both directions

Four fresh Ed25519 keypairs, generated with `openssl genpkey -algorithm
ed25519` and signed with `openssl pkeyutl -sign -rawin` — over a
1-byte, an 11-byte, a 43-byte and a 512-byte message — each confirmed
with `openssl pkeyutl -verify` before being used as a fixture:

| What | Checked how |
|---|---|
| Public key derivation | `public_key_from_seed` on each seed matches the real key `openssl` derived from the same seed, byte for byte, all four vectors |
| Signing | `sign` on each seed+message matches `openssl`'s own signature, byte for byte, all four vectors |
| Verification | `verify` accepts each of `openssl`'s own signatures — including the 512-byte one this module never produced itself — and rejects it once either the signature or the message is tampered with by one bit |

The 512-byte case is the one worth naming: it is verified against a
signature `sign` never touched, over a message longer than one hash
block, the strongest check available without a second independent
implementation to compare every intermediate value against.
`tests/accept/ed25519.ls` carries the first three; `docs/ed25519.md`'s
own history (this document) is where the fourth, cross-direction check
is recorded, since a fixture can only assert what one program computes,
not what an external tool already agreed to.

Both backends agree — `the_two_backends_agree_on_ed25519` in
`crates/lex-sys/tests/conformance/backends.rs`.

## 6. What this module deliberately does not provide

**Not constant-time.** Every branch here — `bn_sub_into`'s borrow,
`bn_modpow`'s bit test, `point_unpack`'s sign correction — is an
ordinary conditional, and an ordinary conditional's timing can depend
on the secret data it branches on. `ed25519-dalek` (what
`lex-os-capsule` uses today) is written specifically to make that hard
to introduce by accident; nothing here makes it hard at all. A
timing-oracle attacker with repeated access to signing under a fixed
key is the threat model this matters for, and this module is not
written against it. Whether that threat model applies depends on where
a future consumer runs this — that is a decision for whoever reaches
for this module next, not one this document can make in advance.

**No key generation from randomness.** `public_key_from_seed`/`sign`
take a caller-supplied 32-byte seed; lex-sys has no CSPRNG capability
today (no `random` in the capability list `linearity-and-effects.md`
settles), so there is nothing this module could call to generate a
fresh one. A caller gets a seed from wherever it already trusts one to
come from.

**No batch or double-scalar multiplication.** `verify`'s `S*B == R +
k*A` check does two full scalar multiplications and a point add, where
a real implementation typically combines them into one double-scalar
multiplication for speed. Correct either way; slower than it needs to
be, which is this module's trade throughout, made once more.
